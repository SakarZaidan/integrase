# 23. Upstream ecosystem strategy

**Status:** decided
**Date:** 2026-09-14
**Decides:** what Integrase builds, what it adopts, and what it contributes back
**Why this subplan exists:** the discovery of `sbol-rs` created a build-versus-adopt decision the
brief could not anticipate, and it fits cleanly in none of the required 22. It is simultaneously a
supply-chain question and a question about the project's relationship with the standards body whose
legitimacy it depends on.
**Feeds:** subplans 05, 06, 17, 19, and `FINAL-DECISION.md`

---

## The decision

**Adopt `sbol-rs` wholesale. Contribute upstream. Build nothing that it already does.**

This is not a close call, and the evidence below is measured rather than assumed. The brief
budgeted for building SBOL support from scratch in Rust. That budget is now free, and the honest
framing in the README is that Integrase depends on `sbol-rs` rather than that Integrase implements
SBOL.

---

## What `sbol-rs` actually is

My first assessment from crates.io metadata was that this was a useful SBOL parser. That
undersold it considerably. Verified by cloning the repository and reading it:

**Fourteen crates**, not one:

```
sbol            umbrella          sbol-genbank    GenBank conversion
sbol2           SBOL 2.3.0        sbol-fasta      FASTA conversion
sbol3           SBOL 3.1.0        sbol-ontology   ontology terms
sbol-core       shared core       sbol-rulegen    validation rule generation
sbol-rdf        RDF layer         sbol-utilities  construction helpers
sbol-convert    SBOL 2 <-> 3      sbol-cli        command-line tool
sbol-bench      benchmarks        sbol-py         Python bindings
```

**Validation coverage:** 109 machine-checkable rules of SBOL 3.1.0 Appendix B, and 239
machine-checkable rules of the SBOL 2.3.0 catalog. That is 348 conformance rules. Implementing
that from scratch would be a multi-month project on its own, and getting it wrong would be
invisible until someone's design silently failed to round-trip.

**Test corpus:** 343 data files across `cross-impl-pysbol3`, `cross-impl-sbol2`,
`cross-impl-sbolconverter`, `fasta`, `genbank`, and `sbol2` fixture sets.

**Engineering posture:** `benches/`, `fuzz/`, `spec/`, `docs/`, CI badges, a `CITATION.cff`, and a
Zenodo DOI. MSRV 1.93, comfortably below our Rust 1.98. Dual MIT OR Apache-2.0, compatible with our
Apache-2.0 choice.

**RDF layer:** built on the Oxigraph family (`oxrdf`, `oxrdfio`, `oxttl`, `oxrdfxml`, `oxjsonld`,
`oxiri`). This answers open question 5 from the research log directly: if we ever need RDF
primitives ourselves, we use the Oxigraph stack, because introducing `sophia` alongside would put
two RDF implementations in one binary for no reason.

**`sbol-py`:** Python bindings that unify SBOL 2 and SBOL 3 in one package, which no other Python
library does (`pysbol2` and `pysbol3` are separate installs with no bridge). Their README claims
8x to 2300x faster than pySBOL3 on parse, validate, and serialize benchmarks. Not yet on PyPI;
built with maturin.

That last point matters for subplan 15's Python SDK design and is discussed below.

## What I verified by running it

Claims in a README are claims. I built a probe against the actual crates and measured. Results:

```
[1] build + validate:             OK (1 object)
[2] turtle round-trip:            1 in, 1 out
[3] pySBOL3 fixture round-trips:  33 lossless, 0 lossy, 0 failed
[4] SBOL2->3->2 on  7 fixtures:   0 triple-identical, 7 differ, 0 errored
```

### Result 3: SBOL3 round-trips are genuinely lossless

All 33 Turtle fixtures in the `cross-impl-pysbol3` set read, re-serialize, and re-read with object
counts preserved and no failures. These fixtures are expected output generated by pySBOL3, so this
is cross-implementation agreement, not self-consistency.

### Result 4: SBOL2 to SBOL3 and back is not triple-identical, and that is correct behaviour

This needs care, because the naive reading of the number is wrong and reporting it as a defect
would be an overclaim.

None of the 7 SBOL2 fixtures produced a byte-for-byte identical triple set after a
2 -> 3 -> 2 round-trip. Measuring what actually differs:

| Fixture | Triples in | out | Lost | Added |
|---|---:|---:|---:|---:|
| `single_cd.ttl` | 14 | 14 | 2 | 2 |
| `collection.ttl` | 18 | 18 | 4 | 4 |
| `cd_with_annotation.ttl` | 27 | 27 | 3 | 3 |
| `cd_with_subparts.ttl` | 32 | 32 | 6 | 6 |
| `md_simple.ttl` | 28 | 30 | 2 | 4 |
| `mapsto_merge.ttl` | 39 | 43 | 1 | 5 |
| `urn_design.ttl` | 6 | 5 | 6 | 5 |

Most rows are symmetric: the same number lost and added, on `sbol:role` and `sbol:type`
predicates. Inspecting the fixtures, those are `sbol:type biopax:Dna` and `sbol:role so:0000167`.
The conversion canonicalizes ontology URIs. Same information, different spelling. That is
normalization, not loss.

`urn_design.ttl` is the one genuine asymmetry, and it is explained by the data models rather than
by a bug. That fixture uses `urn:sbol:design:promoter/1` style URN identifiers with
`sbol:persistentIdentity` and `sbol:version`. SBOL 3 removed the persistentIdentity and version
mechanism and expects HTTP(S) IRIs. A 2 -> 3 -> 2 round-trip therefore cannot reconstruct the
original URN structure, because the intermediate representation has nowhere to put it.

**The honest conclusion: the conversion is semantically faithful but not syntactically idempotent,
and it cannot be, because the two data models genuinely differ.** My triple-identity test was a
stricter criterion than "lossless" means in this context. The result is still valuable, for a
reason that has nothing to do with judging `sbol-rs`.

### What result 4 means for our own testing

**Integrase's SBOL conformance tests must compare at the semantic level, not the triple level.**
A contract test asserting byte or triple equality after a version conversion will fail on correct
behaviour, and someone will then "fix" it by weakening the assertion until it passes, which is how
test suites rot. Subplan 17 needs to specify semantic comparison explicitly, and this measurement
is the reason.

It also means any user-facing claim we make about SBOL 2 to 3 conversion has to carry the same
nuance rather than saying "lossless" flatly. The `sbol-rs` conversion functions return an
`UpgradeReport` and a `DowngradeReport` alongside the converted graph, which is exactly the right
design: the library tells you what it did rather than pretending nothing happened. Surfacing those
reports to the user is well aligned with Integrase's honesty principle, and subplan 06 should treat
them as first-class data to display, not as debug output to discard.

## Consequences for the plan

### 1. We do not implement SBOL. We depend on it.

The `integrase-sbol` crate from subplan 01 changes character entirely. It is no longer an SBOL
implementation. It is a thin adapter between `sbol-rs` types and Integrase's internal design model,
plus the confidence and provenance metadata that SBOL has no place for. That is a week of work
instead of a year, and it is more correct than anything we would have written.

### 2. The Python SDK question is now open in an interesting way

`sbol-py` already provides Rust-backed SBOL for Python, unifying SBOL 2 and 3, faster than
pySBOL3. Integrase's Python SDK should not duplicate any of that. It should depend on it, or on
`sbol` once published to PyPI, and add only what Integrase brings: simulation, calibrated
predictions, and the screening gate.

**Open risk:** `sbol-py` is not yet on PyPI. If it stays unpublished, our Python SDK either bundles
its own maturin build of the bindings, which is a packaging burden, or falls back to pySBOL3 for
the Python path while using `sbol-rs` in Rust, which means two SBOL implementations with different
behaviour in one product. Neither is good. **This is the strongest single reason to open a
conversation with SynBioDex early**, and it is a concrete, useful thing to ask about rather than a
vague offer of collaboration.

### 3. One of our claimed differentiators is gone, and that is fine

Subplan 02 already graded native SBOL support as WEAK. This subplan confirms it more strongly than
that grade implied. "We read SBOL" is not a wedge. What it is instead is a large de-risking: the
hardest correctness problem in the interop story is solved by someone else, with 348 validation
rules and a cross-implementation test corpus we could not have justified building.

### 4. A sobering data point for subplan 03

`sbol-rs` is objectively excellent. Fourteen crates, 348 validation rules, fuzzing, benchmarks,
cross-implementation fixtures, Python bindings that are orders of magnitude faster than the
incumbent, a Zenodo DOI, from the standards body itself.

It has **5 stars.**

That is the clearest available evidence for subplan 03's adoption score of 3 out of 10. In this
field, being substantially better than the incumbent does not produce adoption. Whatever Integrase
builds, quality alone will not get it used, and any plan that assumes otherwise is assuming
something this repository directly contradicts.

## What we contribute back

Being a serious downstream user is the honest basis for a relationship with SynBioDex, and it is
worth more than an introductory email. Concrete contributions available immediately:

1. **Report the `urn_design.ttl` round-trip asymmetry.** Not as a bug report claiming breakage, but
   as a question about intended behaviour, with the measurement attached. If it is intended, it is
   worth documenting; if it is not, we found it. Either outcome is a useful first interaction.
2. **Ask about `sbol-py` on PyPI**, with our use case as the motivation. A downstream project
   wanting to depend on it is the most useful thing a maintainer can hear about publication
   priority.
3. **Contribute fixtures.** Any real-world SBOL file that trips up our adapter is a fixture
   `sbol-rs` would want, and we will accumulate those naturally.
4. **Upstream fixes rather than patching locally.** If we need a change in `sbol-rs`, the default
   is a PR there, not a fork here. Forking a standards-body implementation would be a strategic
   mistake regardless of how convenient it is in the moment.

## Supply chain risk, stated honestly

Depending this heavily on a four-month-old v1.0.0 with 5 stars is a real risk and should not be
waved away because the code is good.

| Risk | Assessment | Mitigation |
|---|---|---|
| Project is abandoned | Moderate. This field abandons things. Cello, SBOLDesigner, paraSBOLv. | Apache-2.0/MIT means we can fork if we must. The adapter boundary in `integrase-sbol` keeps the blast radius contained to one crate. |
| Breaking API changes pre-1.0 stability | Low. It is v1.0.0 with a CHANGELOG and semver. | Pin exact versions, per subplan 07's vetting rules. |
| Correctness bug in validation | Low, given 348 rules, fuzzing, and cross-implementation fixtures. Lower than our own implementation would be. | Our own conformance tests run against the same corpus independently, so we would notice a regression. |
| Single maintainer group | Real. Same bus-factor problem the whole field has. | Contribute, so we understand the codebase well enough to maintain a fork if it ever comes to that. |

**The alternative is worse.** Writing our own SBOL implementation means owning 348 validation rules
we would implement incompletely, a conversion path between two genuinely different data models, and
five serialization formats, with no cross-implementation oracle. The risk of a subtle correctness
bug in our own version far exceeds the risk of this dependency being abandoned.

## Rules that follow from this

These belong in subplan 07's engineering principles and are stated here because this subplan is
where they were earned:

1. **Do not reimplement a standards-body implementation.** If SynBioDex ships it, depend on it.
2. **Adapter boundaries around external implementations.** Anything from `sbol-rs` crosses into
   Integrase through `integrase-sbol` and nowhere else, so a future migration touches one crate.
3. **Conformance tests are ours, independently.** Depending on a library does not mean trusting it
   silently. We test against the corpus ourselves, because that is how we would find out if an
   upgrade broke something.
4. **Semantic comparison, never syntactic, for format round-trips.** Earned directly from result 4.
5. **Upstream first.** A needed change goes to `sbol-rs` as a PR before it goes into a local patch.
