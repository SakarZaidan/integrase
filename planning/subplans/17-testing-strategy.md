# 17. Testing strategy

**Status:** decided
**Date:** 2026-09-14
**Decides:** the test taxonomy, tooling per language, and how scenarios become tests
**Depends on:** subplans 07 (R-2 rules), 11 (scenarios), 24 (screening tests)
**Feeds:** subplan 18 (CI), and every crate's test layout

---

## The governing rule

From subplan 07, **R-2.2: a test that cannot fail is not a test.** Every layer below exists to catch
a specific class of bug, and a test that cannot name the bug it catches gets deleted in review
rather than counted toward coverage.

This is stated first because coverage floors (R-2.1) create pressure toward exactly the tests this
rule forbids: constructors that construct, getters that get, wrappers asserting arithmetic. Those
raise the number and lower the signal.

---

## Layers

### 1. Unit tests

**Rust:** `cargo test`, in-module `#[cfg(test)]` for private logic, `tests/` for public surface.
**Go (Phase 3):** standard `testing`, table-driven.
**Python:** `pytest`.

**What belongs here:** logic with branches. Coordinate arithmetic, alphabet validation, interval
arithmetic, policy threshold comparison, error construction.

**What does not:** anything the type system already guarantees.

### 2. Property-based tests

`proptest` for Rust, `hypothesis` for Python. Required for sequence manipulation and numerical code
(R-2.3), because these are exactly where hand-picked examples miss whole classes of bugs.

Properties that must hold:

| Property | Catches |
|---|---|
| `revcomp(revcomp(s)) == s` | Strand handling, alphabet asymmetry, ambiguity code mishandling |
| Coordinate remapping is consistent under insert/delete/replace | Off-by-one under edits, the endemic bioinformatics bug |
| `Interval` contains its point estimate, always | Arithmetic errors that make a prediction inconsistent with its own bounds |
| Feature locations stay within sequence bounds after any edit | Silent corruption, the worst kind |
| SBOL export then import preserves features semantically | Adapter loss |
| Screening a sequence and its reverse complement agrees | A real evasion vector if it does not |

That last one is worth flagging: it is a property test that doubles as a security test, and it is
the kind of thing an example-based suite would never think to check.

### 3. Contract tests: SBOL conformance

Against the **vendored `sbol-rs` corpus** (343 files, MIT/Apache-2.0), not against live SynBioHub,
which requires authentication (subplan 04). Vendoring is the better answer regardless: CI that
depends on a third-party service is CI that fails for reasons unrelated to the change under test.

**R-2.4 applies absolutely: comparison is semantic, never syntactic.** Established by measurement in
subplan 23: SBOL 2 to 3 conversion canonicalises ontology URIs and cannot preserve
`persistentIdentity`, so a triple-equality assertion fails on correct behaviour, gets weakened until
it passes, and the suite stops meaning anything.

Semantic comparison means: same features, same locations, same roles after ontology normalisation,
same sequence, same hierarchy. Not the same triples.

**The `cross-impl-pysbol3` fixtures are a cross-implementation oracle.** They are expected output
generated by pySBOL3, so disagreement between our path and theirs is worth investigating regardless
of which one turns out to be wrong.

### 4. Integration tests across boundaries

Real request paths through the actual API, not mocks at every seam. Mocking every boundary tests the
mocks.

| Boundary | Exercised how |
|---|---|
| Rust to Python (PyO3) | Python tests calling the built extension, not a stub |
| Rust to screening backend | Against the SecureDNA **test HDB**, which ships in their repository |
| Rust to Go (Phase 3) | Real gRPC over loopback |
| Go to Python ML (Phase 3) | Real gRPC |

The SecureDNA test HDB is what makes the highest-consequence integration test runnable in CI with no
credentials and no production data. Its existence is why subplan 24's delegation decision works.

### 5. The screening suite

Highest consequence of a false negative in the system, so it is the most rigorously tested part
(95% floor, R-2.1) and its own required, non-skippable CI check.

Full requirements are in subplan 24. The structure:

| Class | Assertion |
|---|---|
| **Fail-closed fault injection** | Backend unreachable, timing out, malformed JSON, partial response, panicking: every one produces a refusal. **Never a pass.** |
| `NullBackend` | Refuses everything, including empty input. |
| **Compile-fail** | `trybuild` test proving `export_sbol(&unscreened_design)` does not compile. |
| **Python runtime gate** | Exporting an unscreened design from Python raises. This is the weakened guarantee from subplan 12 and needs its own coverage precisely because the compiler no longer provides it. |
| Boundary | Sequences exactly at threshold length, one below, one above. Matches straddling window boundaries. |
| Reverse complement | Screening agrees on both strands. |
| Policy reproducibility | A verdict under policy v1 reproduces under v1 after v2 exists. |
| Audit integrity | Tampering with any entry breaks the hash chain and is detected. |

The compile-fail test deserves emphasis. It is the only test that verifies the **type-level**
guarantee rather than the runtime behaviour, and without it a refactor could quietly make `Cleared`
constructible elsewhere while every runtime test still passed.

### 6. Model evaluation tests

Per R-2.6, calibration is tested rather than asserted. Subplan 08 owns methodology.

| Test | Fails when |
|---|---|
| Marginal coverage | An 80% interval does not contain the truth ~80% of the time on held-out data |
| **Stratified coverage** | Coverage holds on average but breaks within expression deciles |
| OOD detection rate | Sequences from the independent dataset are not flagged |
| Baseline comparison | The ML layer does not beat the deterministic baseline out-of-distribution (subplan 16, V-3) |
| Interval sanity | Intervals are infinite, inverted, or exclude the point estimate |

**Stratified coverage is the one most likely to catch something real.** A model overconfident on
weak signals and underconfident on strong ones hits 80% marginally while being systematically wrong
in a way users actually experience. Testing only marginal coverage would miss it entirely.

These are **not run on every PR.** They need the evaluation dataset and are slow. They run nightly
and on any PR touching `integrase-sim` or the model artifacts.

### 7. Performance regression tests

`criterion`, gated on subplan 09's Tier 1 numbers only. Tier 2 budgets are not gated until measured,
because gating an unmeasured budget produces a flaky check that people learn to re-run until green.

10% threshold. Memory gated equally with time, since at 39.4 bytes per base a memory regression is a
scope regression: it directly reduces the supported genome size.

### 8. End-to-end scenario tests

Built directly from subplan 11, which was written with this in mind.

| Scenario | Test |
|---|---|
| S1 biologist imports and predicts | `tests/e2e/import_predict.rs` |
| S2 student assembles a construct | `tests/e2e/first_construct.rs` |
| S3 notebook batch prediction | `python/tests/test_notebook_flow.py` |
| S4 self-hosted screening | `tests/integration/custom_backend.rs` |
| E1 partial screening match | `integrase-screen/tests/partial_match.rs` |
| E2 out-of-distribution sequence | `integrase-sim/tests/domain_verdict.rs` |
| E3 oversized genome | `integrase-core/tests/size_limits.rs` |
| E4 backend partition | `integrase-screen/tests/fail_closed.rs` |
| E8 SBOL 2 round-trip | `integrase-sbol/tests/roundtrip.rs` |

### 9. Visual regression

`integrase-viz` has a 60% coverage floor because rendering is hard to unit test honestly. The rest is
carried by **SVG snapshot tests**, which is why `svg.rs` is a deliverable rather than a fallback
(subplan 06): SVG output is deterministic and text-diffable, so a rendering change shows up as a
readable diff rather than an image comparison with a tolerance nobody trusts.

Specifically snapshotted: glyph selection for each SO role, and **the visual encoding of every
`DomainVerdict` variant**. The second matters because confidence cartography silently degrading into
"everything looks equally confident" is a product failure that no functional test would catch.

## What we deliberately do not test

Stated so the gaps are chosen rather than accidental.

| Not tested | Why |
|---|---|
| `sbol-rs` internals | It has 348 validation rules, its own fuzzing, and its own cross-implementation corpus. We test our adapter and our assumptions about its behaviour, not its correctness. |
| SecureDNA's screening accuracy | Peer-reviewed and not ours. We test that we call it correctly and fail closed, not whether its hazard set is right. |
| GPU rendering pixel output | Driver-dependent and would be flaky in CI. SVG snapshots carry the signal. |
| Biological correctness of predictions | **We cannot.** That requires a wet lab. We test that the model implements the published equations and that its stated uncertainty is calibrated. Those are different claims and the docs say so. |

That last row is the important one. No test in this repository establishes that a prediction is
biologically right. Subplan 16 says this plainly and the docs repeat it.

## Tooling

| Concern | Tool |
|---|---|
| Rust unit/integration | `cargo test`, `cargo nextest` in CI for speed and better output |
| Rust properties | `proptest` |
| Rust compile-fail | `trybuild` |
| Rust benchmarks | `criterion` |
| Rust coverage | `cargo llvm-cov` |
| Python | `pytest`, `hypothesis`, `pytest-cov` |
| Go (Phase 3) | standard `testing`, `go test -race` |
| Fault injection | Test doubles implementing `ScreeningBackend` with injected failures |
| Snapshots | `insta` for SVG and serialized structures |

**`go test -race` is non-negotiable in Phase 3.** Concurrency is the reason Go is there at all.

---

## Coverage reporting

Per-subsystem floors from R-2.1, enforced in CI, reported on every PR as a delta rather than an
absolute. An absolute number invites gaming; a delta shows whether this change made things better or
worse, which is the question a reviewer actually has.

**The screening crate's floor is a hard gate.** Others are advisory on a first failure and blocking
on a second, because a mechanical gate that fires on a legitimate refactor teaches people to route
around it.
